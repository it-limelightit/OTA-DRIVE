## Essential Backend/Web Changes

### 1. Publish to the individual device topic

```text
Limelight/factory/<device_id>/config
```

Example:

```text
Limelight/factory/DM-117/config
```

Do not use a shared fleet topic yet. For multiple devices, publish one command to each device topic.

Use:

- QoS: `1`
- Retained: `false`

### 2. Send valid raw JSON

```json
{
  "msg_type": "ota.start",
  "command_id": "a5bc4e31-8e73-4101-9b22-c081d0e762fa",
  "deployment_id": "501ed119-fbf1-4126-9226-f87555914e61",
  "version": "3.1.6",
  "url": "https://firmware.example.com/DM/16/3.1.6/firmware.bin?...",
  "size": 1259296,
  "sha256": "bdb27471004c59c792856a94d3ead05a5cc7143efc37f3a30703291fc024771f"
}
```

Important:

- Use `msg_type`, not `msg\_type`.
- URL must be a plain JSON string—not a Markdown link.
- `size` must be an integer, not a string or decimal.
- Prefer `ota.start`; `private_ota.start` remains supported temporarily.

### 3. Generate correct artifact metadata

Calculate from the exact `.bin` file being served:

```bash
sha256sum firmware.bin
```

The backend must provide:

- Exact byte size
- SHA-256 of the complete `.bin`
- Version matching the ESP application version embedded in the image
- Correct firmware for the device model and flash variant

Do not modify, compress, or regenerate the file after calculating its hash.

### 4. Firmware download endpoint requirements

The download server must:

- Use HTTPS in production
- Return a correct `Content-Length`
- Serve the binary without compression or transformation
- Keep the URL valid for the entire download
- Return HTTP `200`
- Use `application/octet-stream`

Recommended URL expiry: at least 30 minutes. The earlier 15-minute URL is too close to the firmware’s maximum download period.

### 5. Handle OTA status correctly

Subscribe to:

```text
Limelight/factory/<device_id>/ota/status
```

Expected sequence:

```text
ACCEPTED
   ↓
DOWNLOADING
   ↓
VERIFYING
   ↓
INSTALLING
   ↓
Device restarts
   ↓
SUCCESS
```

Do not mark the deployment successful at `INSTALLING`. Only `SUCCESS` after restart confirms the new firmware is running.

A successful message contains:

```json
{
  "msg_type": "ota.status",
  "device_id": "DM-117",
  "deployment_id": "...",
  "command_id": "...",
  "status": "SUCCESS",
  "progress_percent": 100,
  "current_version": "3.1.6"
}
```

### 6. Deployment tracking

The backend should store:

- Device ID
- Command ID
- Deployment ID
- Requested version
- Current status
- Progress
- Error code
- Creation time
- Last status time
- Completed time
- Installed version

Each retry should normally receive a new `command_id`.

### 7. Essential security

- Configure MQTT broker ACLs so a device can access only its own topics.
- Use MQTT over TLS in production.
- Use HTTPS signed URLs.
- Never expose signed URLs in dashboards, application logs, or MQTT status messages.
- Verify the selected firmware belongs to the device’s model and flash variant.
- Do not permit arbitrary user-entered firmware URLs; URLs should be generated by the backend.

The web dashboard should therefore provide device selection, firmware selection, deployment status, progress, installed version, and safe retry—while the backend handles MQTT and signed URL generation.
